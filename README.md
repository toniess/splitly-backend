# Splitly

Сервис учёта общих расходов в группе: кто за что платил, кто кому сколько должен и как закрыть
долги минимальным числом переводов.

Учебный проект на Spring Boot. Техническое задание — [docs/splitly-tz.md](docs/splitly-tz.md).

## Стек

| Что | Выбор |
| --- | --- |
| Язык | Java 21 (LTS) |
| Фреймворк | Spring Boot 4.1.1 |
| Сборка | Gradle (Kotlin DSL), через wrapper |
| БД | PostgreSQL 18 в Docker |
| Доступ к данным | Spring Data JPA (Hibernate) |
| Миграции | Flyway |

## Требования

- **JDK 21** — версия фиксирована в `build.gradle.kts` через toolchain
- **Docker** — для PostgreSQL

Gradle ставить не нужно: в репозитории лежит wrapper, он скачает нужную версию сам.

## Запуск

```bash
cp .env.example .env          # затем вписать пароль в POSTGRES_PASSWORD
docker compose up -d          # PostgreSQL на localhost:5432
./gradlew bootRun --args='--spring.profiles.active=dev'
```

Приложение стартует на `http://localhost:8080`. Flyway накатывает миграции автоматически при
старте.

Из IDE запускается классом `SplitlyApplication`; профиль `dev` указывается в поле
**Active profiles** конфигурации запуска.

## Проверка

```bash
curl localhost:8080/actuator/health
curl localhost:8080/api/v1/version
```

Ожидаемые ответы:

```json
{"status":"UP"}
```

```json
{"name":"splitly","version":"0.0.1-SNAPSHOT","buildTime":"2026-09-19T16:47:38.958Z"}
```

`health` не декоративный: он реально проверяет соединение с базой. Если контейнер не поднят,
статус будет `DOWN`.

## API

Интерактивная документация — **http://localhost:8080/swagger-ui.html**, спецификация в JSON —
`/v3/api-docs`. Генерируется из контроллеров и DTO, отдельно не поддерживается.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/v1/groups` | создать группу; создатель становится участником с ролью `OWNER` |
| `GET /api/v1/groups` | группы, где состоит пользователь |
| `GET /api/v1/groups/{id}` | группа по идентификатору |
| `GET /api/v1/groups/{id}/members` | участники группы |
| `POST /api/v1/groups/join` | вступить по invite-коду |
| `GET /api/v1/version` | версия сборки |

**Временное решение:** аутентификации пока нет (итерация 5), поэтому «кто выполняет действие»
приходит заголовком `X-User-Id`. Когда появится Spring Security, идентификатор будет браться из
контекста безопасности; сигнатуры сервисного слоя при этом не изменятся — он и сейчас принимает
`UUID actorId` аргументом.

Пользователя для ручных проверок можно создать напрямую, регистрации ещё нет:

```bash
docker exec splitly-db psql -U splitly -d splitly -c \
  "INSERT INTO users (email, password_hash, display_name) VALUES ('a@test.dev','stub','Антон') RETURNING id;"
```

### Формат ошибок

Единый для всего API, по RFC 7807:

```json
{
  "type": "https://splitly.dev/errors/validation",
  "title": "Некорректный запрос",
  "status": 400,
  "detail": "Тело запроса не прошло валидацию",
  "instance": "/api/v1/groups",
  "traceId": "e63ba7b7-6a6c-41e1-9cf3-b39368ddaf87",
  "errors": [{ "field": "name", "message": "не должно быть пустым" }]
}
```

Собирается в `common/GlobalExceptionHandler`. Доменные исключения наследуют `NotFoundException`
или `ConflictException` из `common/exception/`, а обработчик ловит по базовому типу — поэтому
на каждую категорию нужен один метод, а не один на каждое исключение.

`traceId` возвращается клиенту и пишется в лог: по нему находится запись о конкретном сбое.
В ответе 500 наружу не уходит ничего, кроме него.

## Структура

```
src/main/java/dev/toniess/splitly/
├── SplitlyApplication.java   точка входа, корень component scan
├── common/                   обработчик ошибок, базовые исключения, общие DTO
├── user/                     сущность и репозиторий пользователя
└── group/                    группы, участники, вступление по коду
    ├── GroupController.java  разбор HTTP и валидация
    ├── GroupService.java     бизнес-логика и границы транзакций
    ├── dto/                  record-и запросов и ответов
    ├── entity/               сущности JPA
    └── exception/

src/main/resources/
├── application.yml           общее для всех сред
├── application-dev.yml       локальная разработка
└── db/migration/             SQL-миграции Flyway
```

Пакеты группируются по функциям (`group/`, `expense/`, `balance/`), а не по слоям.
Внутри каждого — `XxxController`, `XxxService`, `XxxRepository`, `dto/`, `entity/`.

## База данных

Схема пишется вручную в SQL-миграциях, а не генерируется из сущностей.

```
src/main/resources/db/migration/
└── V1__users_and_auth.sql
```

**Применённая миграция неизменяема.** Flyway хранит контрольную сумму каждого файла; правка
уже применённого файла ломает checksum и роняет приложение при старте. Ошибка исправляется
новой миграцией.

Полезное:

```bash
# структура таблицы
docker exec splitly-db psql -U splitly -d splitly -c '\d users'

# что применено
docker exec splitly-db psql -U splitly -d splitly \
  -c 'SELECT version, description, success FROM flyway_schema_history;'

# проверить миграцию, не применяя её (DDL в PostgreSQL транзакционный)
docker exec -i splitly-db psql -U splitly -d splitly -v ON_ERROR_STOP=1 <<'SQL'
BEGIN;
-- содержимое миграции
ROLLBACK;
SQL
```

Сбросить базу до нуля:

```bash
docker compose down -v && docker compose up -d
```

Флаг `-v` удаляет том с данными. Без него переменные `POSTGRES_*` из `docker-compose.yml`
не применятся повторно — они читаются только при инициализации пустого тома.

## Принятые решения

**`ddl-auto: validate`.** Hibernate сверяет сущности со схемой и падает при расхождении, но
ничего не создаёт и не меняет. Единственный источник правды о схеме — миграции Flyway. Режим
`update` запрещён: он умеет только добавлять, никогда не удаляет, и схема незаметно расходится
между машинами.

**`open-in-view: false`.** По умолчанию Spring держит Hibernate-сессию открытой на всё время
обработки запроса, включая сериализацию ответа. Это маскирует N+1: ленивые связи тихо
догружаются при рендеринге JSON. С выключенным флагом проблема проявляется как ошибка, а не
как тихая просадка производительности.

**Уникальность email — функциональный индекс `lower(email)`, а не `UNIQUE(email)`.** Обычное
ограничение чувствительно к регистру и пропустило бы `Ivan@mail.ru` и `ivan@mail.ru` как два
аккаунта. Индекс не отменяет нормализацию в коде: запросы вида `WHERE email = ?` его не
используют, поэтому email всё равно приводится к нижнему регистру перед обращением к базе.
Индекс — страховка на случай пропущенной ветки кода.

**UUID как первичный ключ, `gen_random_uuid()` по умолчанию.** Клиент может сгенерировать id
сам — это нужно для идемпотентности и офлайн-режима мобильного приложения.

**`TIMESTAMPTZ` для всех временных меток, хранение в UTC.** `TIMESTAMP` без зоны делает
записи из разных часовых поясов неразличимыми и неправильно сортируемыми.

**Деньги — `NUMERIC(19,4)` в базе и `BigDecimal` в коде**, `scale = 2`, `RoundingMode.HALF_UP`.
Никогда `double`. Сравнение только через `compareTo`: `equals` у `BigDecimal` учитывает scale,
и `10.0` не равно `10.00`.

**Секреты в `.env`**, который в `.gitignore`. `.env.example` коммитится и служит документацией
по набору переменных. Файл читают оба инструмента: Docker Compose — штатно, Spring — через
`spring.config.import: optional:file:.env[.properties]`.

**Сущности не покидают сервисный слой.** Публичные методы `GroupService` возвращают DTO, а не
`Group` и `GroupMember`. Это не стилистика: `open-in-view` выключен, поэтому обращение к ленивой
связи за пределами транзакции бросает `LazyInitializationException`. Маппинг обязан происходить
внутри `@Transactional`-метода.

**Связи `@ManyToOne` объявлены как `LAZY` явно.** По умолчанию JPA использует `EAGER`, и каждая
загрузка участника молча тянула бы группу и пользователя отдельными запросами. Нужные связи
подгружаются точечно, через `JOIN FETCH` в конкретном запросе.

**Коллекций `@OneToMany` в сущностях нет.** Списки берутся запросами репозитория. Двунаправленные
связи превращают загрузку одного объекта в обход графа, который невозможно контролировать.

**Уникальность — ограничением базы, а не проверкой в коде.** `UNIQUE(group_id, user_id)` и
`UNIQUE(invite_code)` держатся на уровне PostgreSQL: проверка `SELECT` перед `INSERT` не спасает
от двух параллельных запросов, которые оба увидят «свободно».

**Роль участника — `enum` с `@Enumerated(EnumType.STRING)`.** Режим по умолчанию `ORDINAL` пишет
в базу порядковый номер константы: добавление значения в середину перечисления молча меняет
смысл всех существующих строк.

## Что понял в итерации 1

> Этот раздел нужно переписать своими словами — он ведётся для себя, а не для читателя.

Spring Boot не «настраивается», а выводит конфигурацию из classpath: положил драйвер и
стартер JPA — получил пул соединений, положил Flyway — получил миграции при старте. Отчёт о
том, что именно включилось и почему нет остального, печатается при запуске с `--debug`.

Профили — это не «настройки для разработки», а способ описать одно приложение в разных средах.
Ключ кладётся в общий файл, если его значение не зависит от среды, и в файл профиля, если
зависит. Ошибка в раскладке проявляется не сразу: тест запускается без профиля `dev` и не видит
того, что лежит только там.

Классы создаёт не мой код: `@SpringBootApplication` задаёт корень сканирования, всё под этим
пакетом превращается в бины, зависимости объявляются параметрами конструктора и подставляются
контейнером.

## Что понял в итерации 2

> Тоже переписать своими словами.

Границы транзакции — это решение, а не формальность. `@Transactional` работает через прокси,
поэтому не действует на непубличных методах и при вызове изнутри того же класса. Откат по
умолчанию происходит только на `RuntimeException`: проверяемое исключение оставляет транзакцию
закоммиченной, поэтому доменные ошибки — наследники `RuntimeException`.

N+1 — это не абстракция, его видно. Список участников без `JOIN FETCH` стоил одного запроса на
каждого участника; с ним — одного на всех. Проверяется подсчётом строк `Hibernate:` в логе
dev-профиля, и именно ради этого включены `show-sql` и выключен `open-in-view`.

Между «сохранил» и «записалось в базу» есть зазор. `save()` только помещает сущность в
persistence context, реальный `INSERT` уходит при сбросе — поэтому `@CreationTimestamp` не был
заполнен в ответе, пока не появился `saveAndFlush`. По той же причине нарушение уникального
ограничения всплывает не там, где ожидаешь.

Три бага в маппинге DTO нашлись только ручной проверкой через `curl`: компилятор их не видит,
типы совпадают. Это аргумент в пользу тестов на мапперы, даже когда код выглядит тривиальным.
