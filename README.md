# Splitly

Сервис учёта общих расходов в группе: кто за что платил, кто кому сколько должен и как закрыть
долги минимальным числом переводов.

Учебный проект на Spring Boot. Техническое задание — [docs/splitly-tz.md](docs/splitly-tz.md).

## Стек

| Что | Выбор |
| --- | --- |
| Язык | Java 21 (LTS) |
| Фреймворк | Spring Boot 4.1.1 |
| Сборка | Gradle (Kotlin DSL), через wrapper |
| БД | PostgreSQL 18 в Docker |
| Доступ к данным | Spring Data JPA (Hibernate) |
| Миграции | Flyway |

## Требования

- **JDK 21** — версия фиксирована в `build.gradle.kts` через toolchain
- **Docker** — для PostgreSQL

Gradle ставить не нужно: в репозитории лежит wrapper, он скачает нужную версию сам.

## Запуск

```bash
cp .env.example .env          # затем вписать пароль в POSTGRES_PASSWORD
docker compose up -d          # PostgreSQL на localhost:5432
./gradlew bootRun --args='--spring.profiles.active=dev'
```

Приложение стартует на `http://localhost:8080`. Flyway накатывает миграции автоматически при
старте.

Из IDE запускается классом `SplitlyApplication`; профиль `dev` указывается в поле
**Active profiles** конфигурации запуска.

## Проверка

```bash
curl localhost:8080/actuator/health
curl localhost:8080/api/v1/version
```

Ожидаемые ответы:

```json
{"status":"UP"}
```

```json
{"name":"splitly","version":"0.0.1-SNAPSHOT","buildTime":"2026-09-19T16:47:38.958Z"}
```

`health` не декоративный: он реально проверяет соединение с базой. Если контейнер не поднят,
статус будет `DOWN`.

### Деньги в JSON

Суммы передаются **строкой** с двумя знаками: `"1234.50"`. Числом нельзя — в JavaScript все
числа это `double`, и значение теряет точность ещё до того, как клиент его увидит.

В базе хранится `NUMERIC(19,4)`: четыре знака нужны как запас на промежуточные вычисления,
наружу отдаётся два. Нормализация и сериализация — в `config/JacksonConfig`, правила — в
`common/Money`.

### Деление траты

Три стратегии, выбираются полем `splitType`:

| Тип | Что в `participants[].value` | Что делает сервер |
| --- | --- | --- |
| `EQUAL` | не используется | делит поровну, остаток раздаёт по копейке |
| `SHARES` | вес (`1`, `2`, `3`) | делит пропорционально весам |
| `EXACT` | готовая сумма | **ничего не считает**, только проверяет равенство сумме траты |

Для `EQUAL` и `SHARES` присланные клиентом суммы игнорируются: иначе подменённое приложение
записало бы себе долю в копейку. Остаток от округления раздаётся по одной минимальной единице
участникам, отсортированным по `userId`, — порядок детерминирован, пересчёт даёт тот же результат.

### Курсорная пагинация ленты

```
GET /api/v1/groups/{id}/expenses?limit=20&cursor=<opaque>
→ { "items": [...], "nextCursor": "MjAyNi0xMC0..." | null }
```

Не `offset`: при листании кто-то добавляет трату, всё съезжает на позицию, и клиент видит
записи дважды. Курсор указывает не «пропусти N», а «дай то, что идёт после вот этой записи».

Внутри курсора пара `(spentAt, id)`, закодированная в Base64. Пара, а не только время: у двух
трат момент может совпасть, и тогда граница страницы неоднозначна — идентификатор работает
тай-брейкером. Под этот запрос заложен индекс `(group_id, spent_at DESC)`.

Курсор непрозрачен: клиент его не разбирает, иначе формат нельзя будет изменить.

### Аутентификация

Все эндпоинты, кроме `/api/v1/auth/**`, `/actuator/health`, `/actuator/info` и Swagger,
требуют заголовок:

```
Authorization: Bearer <accessToken>
```

Токен выдаёт `POST /api/v1/auth/login`. В Swagger UI есть кнопка **Authorize** — туда вставляется
сам токен, без слова `Bearer`.

| Токен | Живёт | Где хранится | Можно отозвать |
| --- | --- | --- | --- |
| **access** | 15 минут | только у клиента | нет — поэтому короткий |
| **refresh** | 30 дней | хэш в таблице `refresh_tokens` | да |

Access — это подписанный JWT: сервер проверяет подпись своим секретом и не ходит в базу.
Содержимое читается кем угодно (base64, не шифрование), поэтому внутри только идентификатор
пользователя и сроки — ни email, ни ролей.

Refresh — случайная строка на 256 бит. В базе лежит её SHA-256, а не она сама: утечка таблицы
не даёт войти ни за кого.

**Ротация.** Каждое обновление гасит предыдущий refresh-токен. Если приходит уже отозванный —
значит, им пользуются повторно, и все токены пользователя отзываются разом. Этот отзыв идёт в
отдельной транзакции (`REQUIRES_NEW`): внешняя откатится вместе с исключением, а защитная мера
должна сохраниться.

Секрет подписи — переменная окружения `JWT_SECRET`, в репозитории её нет. Сгенерировать:
`openssl rand -base64 48`. Короче 256 бит приложение не стартует.

Пользователя для ручных проверок можно создать напрямую, регистрации ещё нет:

```bash
docker exec splitly-db psql -U splitly -d splitly -c \
  "INSERT INTO users (email, password_hash, display_name) VALUES ('a@test.dev','stub','Антон') RETURNING id;"
```

### Балансы и взаиморасчёты

Сальдо участника — это **вычисляемая величина**, в базе её нет:

```
balance(u) = Σ(траты, где u плательщик)
           − Σ(доли u)
           + Σ(переводы, отправленные u)
           − Σ(переводы, полученные u)
```

Положительное сальдо означает, что человеку должны. Удалённые траты не участвуют.
Сумма сальдо всех участников всегда равна нулю — это проверяется в сервисе на каждом запросе и
отдельным тестом на случайном наборе из 50 трат.

Считается **одним агрегирующим SQL-запросом** (`UNION ALL` по четырём слагаемым плюс внешняя
группировка), а не выгрузкой трат в память. Ориентир ТЗ — 10 участников и 500 трат за 200 мс —
достижим только так. Результат ложится не в сущность, а в интерфейс-проекцию `BalanceProjection`.

Запрос ведётся от `group_members`: в ответ попадают **текущие** участники, в том числе те, кто
ещё ни за что не платил (сальдо `0.00`). Вышедшие не попадают.

**План взаиморасчётов** (`/settlement-plan`) — жадный алгоритм: крупнейший должник платит
крупнейшему кредитору, повторяем. Для N участников получается не больше N−1 переводов вместо
N×(N−1)/2 попарных. Строго оптимальное решение NP-трудно, но на группах из 5–15 человек
разница незаметна.

План **не сохраняется**: это подсказка, вычисляемая на лету и устаревающая при первой же новой
трате. В базу попадает только `Settlement` — факт реального возврата денег.

### Формат ошибок

Единый для всего API, по RFC 7807:

```json
{
  "type": "https://splitly.dev/errors/validation",
  "title": "Некорректный запрос",
  "status": 400,
  "detail": "Тело запроса не прошло валидацию",
  "instance": "/api/v1/groups",
  "traceId": "e63ba7b7-6a6c-41e1-9cf3-b39368ddaf87",
  "errors": [{ "field": "name", "message": "не должно быть пустым" }]
}
```

Собирается в `common/GlobalExceptionHandler`. Доменные исключения наследуют `NotFoundException`
или `ConflictException` из `common/exception/`, а обработчик ловит по базовому типу — поэтому
на каждую категорию нужен один метод, а не один на каждое исключение.

`traceId` возвращается клиенту и пишется в лог: по нему находится запись о конкретном сбое.
В ответе 500 наружу не уходит ничего, кроме него.

## База данных

Схема пишется вручную в SQL-миграциях, а не генерируется из сущностей.

```
src/main/resources/db/migration/
└── V1__users_and_auth.sql
```

**Применённая миграция неизменяема.** Flyway хранит контрольную сумму каждого файла; правка
уже применённого файла ломает checksum и роняет приложение при старте. Ошибка исправляется
новой миграцией.

Полезное:

```bash
# структура таблицы
docker exec splitly-db psql -U splitly -d splitly -c '\d users'

# что применено
docker exec splitly-db psql -U splitly -d splitly \
  -c 'SELECT version, description, success FROM flyway_schema_history;'

# проверить миграцию, не применяя её (DDL в PostgreSQL транзакционный)
docker exec -i splitly-db psql -U splitly -d splitly -v ON_ERROR_STOP=1 <<'SQL'
BEGIN;
-- содержимое миграции
ROLLBACK;
SQL
```

Сбросить базу до нуля:

```bash
docker compose down -v && docker compose up -d
```

Флаг `-v` удаляет том с данными. Без него переменные `POSTGRES_*` из `docker-compose.yml`
не применятся повторно — они читаются только при инициализации пустого тома.

## Принятые решения

**`ddl-auto: validate`.** Hibernate сверяет сущности со схемой и падает при расхождении, но
ничего не создаёт и не меняет. Единственный источник правды о схеме — миграции Flyway. Режим
`update` запрещён: он умеет только добавлять, никогда не удаляет, и схема незаметно расходится
между машинами.

**`open-in-view: false`.** По умолчанию Spring держит Hibernate-сессию открытой на всё время
обработки запроса, включая сериализацию ответа. Это маскирует N+1: ленивые связи тихо
догружаются при рендеринге JSON. С выключенным флагом проблема проявляется как ошибка, а не
как тихая просадка производительности.

**Уникальность email — функциональный индекс `lower(email)`, а не `UNIQUE(email)`.** Обычное
ограничение чувствительно к регистру и пропустило бы `Ivan@mail.ru` и `ivan@mail.ru` как два
аккаунта. Индекс не отменяет нормализацию в коде: запросы вида `WHERE email = ?` его не
используют, поэтому email всё равно приводится к нижнему регистру перед обращением к базе.
Индекс — страховка на случай пропущенной ветки кода.

**UUID как первичный ключ, `gen_random_uuid()` по умолчанию.** Клиент может сгенерировать id
сам — это нужно для идемпотентности и офлайн-режима мобильного приложения.

**`TIMESTAMPTZ` для всех временных меток, хранение в UTC.** `TIMESTAMP` без зоны делает
записи из разных часовых поясов неразличимыми и неправильно сортируемыми.

**Деньги — `NUMERIC(19,4)` в базе и `BigDecimal` в коде**, `scale = 2`, `RoundingMode.HALF_UP`.
Никогда `double`. Сравнение только через `compareTo`: `equals` у `BigDecimal` учитывает scale,
и `10.0` не равно `10.00`.

**Секреты в `.env`**, который в `.gitignore`. `.env.example` коммитится и служит документацией
по набору переменных. Файл читают оба инструмента: Docker Compose — штатно, Spring — через
`spring.config.import: optional:file:.env[.properties]`.

**Сущности не покидают сервисный слой.** Публичные методы `GroupService` возвращают DTO, а не
`Group` и `GroupMember`. Это не стилистика: `open-in-view` выключен, поэтому обращение к ленивой
связи за пределами транзакции бросает `LazyInitializationException`. Маппинг обязан происходить
внутри `@Transactional`-метода.

**Связи `@ManyToOne` объявлены как `LAZY` явно.** По умолчанию JPA использует `EAGER`, и каждая
загрузка участника молча тянула бы группу и пользователя отдельными запросами. Нужные связи
подгружаются точечно, через `JOIN FETCH` в конкретном запросе.

**Коллекций `@OneToMany` в сущностях нет — кроме долей траты.** Списки берутся запросами
репозитория: двунаправленные связи превращают загрузку одного объекта в обход графа, который
невозможно контролировать. Исключение одно — `Expense.shares`: трата и её доли это агрегат, они
создаются и изменяются вместе, между ними есть инвариант «сумма долей равна сумме траты», и доля
вне своей траты не имеет смысла. Отсюда `cascade = ALL` и `orphanRemoval = true`: пересчёт долей
при редактировании сводится к замене содержимого коллекции.

**Ограничение `UNIQUE(expense_id, user_id)` объявлено `DEFERRABLE INITIALLY DEFERRED`**
(миграция V5). При пересчёте долей Hibernate выполняет вставки раньше удалений, и в середине
транзакции в таблице на мгновение оказываются дубликаты, хотя итоговое состояние корректно.
Ограничение описывает именно итоговое состояние, поэтому проверяется при коммите.

**Уникальность — ограничением базы, а не проверкой в коде.** `UNIQUE(group_id, user_id)` и
`UNIQUE(invite_code)` держатся на уровне PostgreSQL: проверка `SELECT` перед `INSERT` не спасает
от двух параллельных запросов, которые оба увидят «свободно».

**`Balance` не сущность и не таблица.** Сальдо вычисляется запросом по тратам, долям и
переводам. Заводить под него таблицу — денормализация, которая немедленно начнёт расходиться
с источником; по ТЗ это делается только при доказанной необходимости.

**Фиксировать перевод может только его отправитель.** Он заявляет «я отдал деньги», и сервер
верит на слово — злоупотребление возможно. Зеркальный вариант (подтверждает получатель)
безопаснее для кредитора; по-настоящему задачу решает двустороннее подтверждение, но это
отдельная фича со статусами, и в скоуп MVP она не входит.

**Выход из группы запрещён при ненулевом сальдо** (409). На этом правиле держится корректность
балансов: вышедший исчезает из выборки, и если бы он уносил с собой ненулевое сальдо, сумма
перестала бы быть нулевой.

**При выходе владельца владение переходит** участнику с наименьшим `userId` — детерминированно.
Последний участник выйти может: группа остаётся пустой, сама запись о ней не удаляется.

**Пароли — BCrypt с cost 12.** Соль и параметры лежат внутри хэша, отдельного столбца не нужно.
Проверка занимает около ста миллисекунд: для пользователя незаметно, для перебора — дорого.

**Правила состава пароля не проверяются**, только длина (8–72). Требование «заглавная, цифра,
спецсимвол» на практике даёт предсказуемые пароли вида `Password1!` и мешает длинным парольным
фразам, которые надёжнее. Верхняя граница не произвольна: BCrypt обрезает вход на 72 байтах.

**На входе проверяется только наличие полей, не формат.** Любая ошибка — неизвестный email,
неверный пароль, невалидный адрес — даёт одинаковый ответ 401 с одним и тем же текстом. Иначе
эндпоинт превращается в проверку, зарегистрирован ли адрес.

**Фильтр не бросает исключений.** Задача JWT-фильтра — положить пользователя в контекст, если
токен валиден, и ничего не делать иначе. Решение об отказе принимает цепочка, а ответ формирует
`AuthenticationEntryPoint`. Исключение, вылетевшее из фильтра, обходит `@RestControllerAdvice` и
приводит к ответу с чужого пути `/error`.

**Роль участника — `enum` с `@Enumerated(EnumType.STRING)`.** Режим по умолчанию `ORDINAL` пишет
в базу порядковый номер константы: добавление значения в середину перечисления молча меняет
смысл всех существующих строк.

## Тесты

```bash
./gradlew test     # только тесты
./gradlew build    # сборка + тесты
```

Тесты идут на настоящем PostgreSQL, не на H2 — иначе они зелёные при сломанном проде
(`NUMERIC`, `TIMESTAMPTZ`, поведение транзакций у H2 отличаются).

Сейчас тесты требуют поднятого `docker compose`. В итерации 6 это заменит Testcontainers,
который поднимет базу сам.

| Что | Чем |
| --- | --- |
| Стратегии деления, реестр, курсор | юнит-тесты, без Spring и без базы |
| Сервис трат | `@SpringBootTest` на настоящей базе |

Интеграционные тесты помечены `@Transactional`: каждый выполняется в своей транзакции, которая
по окончании откатывается. База остаётся нетронутой, тесты не зависят друг от друга и не
требуют очистки.

Отдельно стоит отметить тест инварианта в стратегиях: он прогоняет тысячу случайных сумм и
наборов весов и проверяет, что сумма долей равна сумме траты, а каждая доля отличается от точной
не больше чем на копейку. Такая проверка находит то, чего не видно в примерах с круглыми
числами.

## Что понял в итерации 1

> Этот раздел нужно переписать своими словами — он ведётся для себя, а не для читателя.

Spring Boot не «настраивается», а выводит конфигурацию из classpath: положил драйвер и
стартер JPA — получил пул соединений, положил Flyway — получил миграции при старте. Отчёт о
том, что именно включилось и почему нет остального, печатается при запуске с `--debug`.

Профили — это не «настройки для разработки», а способ описать одно приложение в разных средах.
Ключ кладётся в общий файл, если его значение не зависит от среды, и в файл профиля, если
зависит. Ошибка в раскладке проявляется не сразу: тест запускается без профиля `dev` и не видит
того, что лежит только там.

Классы создаёт не мой код: `@SpringBootApplication` задаёт корень сканирования, всё под этим
пакетом превращается в бины, зависимости объявляются параметрами конструктора и подставляются
контейнером.

## Что понял в итерации 2

> Тоже переписать своими словами.

Границы транзакции — это решение, а не формальность. `@Transactional` работает через прокси,
поэтому не действует на непубличных методах и при вызове изнутри того же класса. Откат по
умолчанию происходит только на `RuntimeException`: проверяемое исключение оставляет транзакцию
закоммиченной, поэтому доменные ошибки — наследники `RuntimeException`.

N+1 — это не абстракция, его видно. Список участников без `JOIN FETCH` стоил одного запроса на
каждого участника; с ним — одного на всех. Проверяется подсчётом строк `Hibernate:` в логе
dev-профиля, и именно ради этого включены `show-sql` и выключен `open-in-view`.

Между «сохранил» и «записалось в базу» есть зазор. `save()` только помещает сущность в
persistence context, реальный `INSERT` уходит при сбросе — поэтому `@CreationTimestamp` не был
заполнен в ответе, пока не появился `saveAndFlush`. По той же причине нарушение уникального
ограничения всплывает не там, где ожидаешь.

Три бага в маппинге DTO нашлись только ручной проверкой через `curl`: компилятор их не видит,
типы совпадают. Это аргумент в пользу тестов на мапперы, даже когда код выглядит тривиальным.

## Что понял в итерации 3

> Переписать своими словами.

Деньги не делятся дробями. Любой алгоритм распределения нужно вести в целых минимальных
единицах: перевёл сумму в копейки, поделил целочисленно, раздал остаток по одной — и терять
нечего. Попытка делить `BigDecimal` на `BigDecimal` с округлением приводит к тому, что сумма
долей не сходится с суммой траты, причём не всегда, а на отдельных входных данных.

Тест ловит ошибку, только если его утверждение различает правильное и неправильное поведение.
Тысяча случайных прогонов с проверкой «сумма сходится» пропускала несправедливое распределение
остатка, потому что сумма в обоих случаях одинаковая. Поймала его проверка «каждая доля
отличается от точной не больше чем на копейку».

Hibernate отправляет изменения в своём порядке, а не в том, в котором они сделаны: вставки
раньше удалений. На замене долей это даёт нарушение уникального ограничения при корректном
итоговом состоянии.

`==` для объектов сравнивает ссылки, и для `UUID` это всегда «не равны». Ошибка компилируется,
не подсвечивается и ломает проверку прав целиком. Инспекция IDE ловит её мгновенно — стоило
включить раньше.

Коды ответов различают, чья ошибка: 400 — тело не разобралось, 422 — данные корректны, но
нарушают бизнес-правило, 409 — состояние системы изменилось, 403 — видишь, но нельзя, 404 —
не должен знать, что объект существует.

## Что понял в итерации 4

> Переписать своими словами.

Есть разница между тем, что хранят, и тем, что вычисляют. Сальдо выводится из трат, долей и
переводов — отдельная таблица под него означала бы два источника правды, которые разойдутся при
первой же забытой синхронизации. Цена вычисления — агрегирующий запрос, и он на порядки дешевле
выгрузки сущностей в память.

Инварианты в системе опираются друг на друга. «Сумма сальдо равна нулю» держится на том, что
выйти из группы с долгом нельзя: уберёшь второе правило — сломается первое, причём не сразу и не
очевидно.

SQL отлаживается в `psql`, а не через перезапуск приложения. Запрос собирается по кускам: одна
ветка — проверил, вторая — проверил, объединил — проверил. Эталон считается руками на бумаге до
того, как написана первая строка.

Потерянный фильтр не ломает запрос, а тихо меняет ответ. Пропавшее `WHERE group_id` в подзапросе
дало сальдо `945.67` вместо `−53.33`: ничего не упало, никто не заметил бы без теста, который
специально проверяет изоляцию групп.

Ошибки с перепутанными аргументами одного типа компилятор не ловит. За итерацию их было четыре:
`expenseId` вместо `actorId`, `toUserId` вместо `fromUserId`, `fromUserId` вместо `toUserId`,
`user_id` без `group_id`. Все нашлись либо прогоном через HTTP, либо тестом — глазами ни одна.

## Что понял в итерации 5

> Переписать своими словами.

Spring Security работает фильтрами, то есть **до** `DispatcherServlet`. Поэтому
`@RestControllerAdvice` не ловит её ошибки: 401 и 403 формируют `AuthenticationEntryPoint` и
`AccessDeniedHandler`, которые пишут ответ в поток сами. Пока их нет, единый формат ошибок
действует только на половину ответов.

Исключение, выброшенное из фильтра, не исчезает — оно улетает в контейнер, тот делает
error-dispatch на `/error`, цепочка отрабатывает повторно и отвечает 401. Код получается
правильный случайно, а в `instance` оказывается `/error` вместо настоящего пути. Разницу видно
только если посмотреть на тело ответа.

Отсутствие `@Transactional` не падает, а молча ничего не сохраняет. Сущность, прочитанная вне
транзакции, сразу detached: меняешь поле — изменение остаётся в памяти и умирает с методом.
Ротация токенов «работала», возвращала 200 и не отзывала ничего.

Откат транзакции отменяет и защитные действия. Массовый отзыв токенов при обнаружении повторного
использования выполнялся прямо перед `throw` — и откатывался вместе с ним. Спасает только
отдельная транзакция в отдельном бине: `REQUIRES_NEW` внутри своего класса не работает, вызов
не проходит через прокси.

Замена `X-User-Id` на контекст безопасности затронула 14 строк в трёх контроллерах и ни одной —
в сервисах и тестах. Это и есть цена, которую окупает разделение слоёв: смена механизма
аутентификации не вышла за пределы слоя, который за неё отвечает.

Подделать токен, поменяв последний символ, не получается: в base64 последний символ кодирует
неполный байт, и несколько разных символов дают одну и ту же подпись. Тест «подделанная подпись»
сначала проходил с кодом 200 именно поэтому — менять надо полезную нагрузку.
