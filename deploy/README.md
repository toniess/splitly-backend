# Развёртывание

Приложение работает в **Cloud.ru Evolution Container Apps**, база — в **Neon**.
Виртуальной машины нет: образ отдаётся платформе, она сама занимается HTTPS,
маршрутизацией и масштабированием.

```
   интернет ──HTTPS──> Container Apps ──TLS──> Neon
                       (наш образ)            (Postgres 18)
```

## 1. Neon

Проект → Postgres **18**, регион ближе к облаку.

Нужна **прямая** строка подключения — та, где в имени хоста **нет** `-pooler`.
Flyway берёт advisory lock на время миграции, а пул Neon работает в transaction
mode и такую блокировку не удержит.

`sslmode=require` обязателен: Neon отвергает незашифрованные соединения.

```
jdbc:postgresql://ep-XXXX.REGION.neon.tech:5432/splitly?sslmode=require
```

Миграции `V1`–`V9` накатятся сами при первом старте приложения.

## 2. Artifact Registry

Создать приватный реестр. При создании выдаются **Key ID** и **Key Secret** —
Key Secret показывается один раз, сохрани сразу.

Адрес реестра выглядит как `<имя-реестра>.cr.cloud.ru`.

Образ собирается и отправляется автоматически при пуше в `main` — см. раздел
«Автоматическая сборка». Вручную, если нужно:

```bash
docker login <имя-реестра>.cr.cloud.ru -u <key_id> -p <key_secret>
./deploy/build-and-push.sh <имя-реестра>.cr.cloud.ru
```

Платформа `--platform` не прощает: на Apple Silicon обычный `docker build`
даёт arm64, и контейнер падает с `exec format error` без внятного объяснения.

## 3. Контейнер в Container Apps

| Поле | Значение |
| --- | --- |
| Образ | `<реестр>/splitly:<тег>` |
| Порт | `8080` |
| Минимум экземпляров | `1` (см. ниже) |

Платформа кладёт значение поля «Порт» в переменную `PORT` и не даёт её
переопределить — приложение читает её само (`server.port: ${PORT:8080}`).

**Переменные окружения:**

```
SPRING_PROFILES_ACTIVE=prod
SPRING_DATASOURCE_URL=jdbc:postgresql://ep-XXXX.neon.tech:5432/splitly?sslmode=require
SPRING_DATASOURCE_USERNAME=...
SPRING_DATASOURCE_PASSWORD=...
JWT_SECRET=...
```

`JWT_SECRET` для прода генерируется заново, локальный не переносится:

```bash
openssl rand -base64 48
```

**Проба живости:**

| Поле | Значение |
| --- | --- |
| Путь | `/actuator/health/liveness` |
| Начальная задержка | `60` с |
| Периодичность | `30` с |

Важно взять именно `liveness`, а не общий `/actuator/health`: последний
проверяет соединение с базой, и спящий Neon выглядел бы как мёртвое
приложение — платформа перезапускала бы контейнер по кругу.

## Масштабирование до нуля

Платформа умеет гасить все экземпляры при простое, и Neon на бесплатном тарифе
делает то же самое. Если спят оба, первый запрос ждёт сумму двух пробуждений:
старт JVM плюс подъём базы — около десяти секунд.

Для демонстрации это плохо: проверяющий решит, что сервис не работает.
Поэтому **минимум экземпляров — 1**. Если важнее экономия, поставь `0` и помни
про задержку первого запроса.

## 4. Домен

В настройках контейнера привязать `api.toniess.dev` и создать у регистратора
`toniess.dev` запись, которую покажет платформа (обычно CNAME на её хост).
Сертификат платформа выпускает сама.

## 5. Проверка

```bash
curl https://api.toniess.dev/actuator/health
curl https://api.toniess.dev/api/v1/version

# полный сценарий: регистрация, вход, создание группы
curl -X POST https://api.toniess.dev/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"test@toniess.dev","password":"password123","displayName":"Тест"}'
```

## Автоматическая сборка

`.github/workflows/publish.yml` запускается при пуше в `main`: прогоняет тесты,
собирает образ под `linux/amd64` и отправляет в реестр с двумя тегами —
`sha-<полный хеш коммита>` и `latest`.

В настройках репозитория на GitHub нужно завести:

| Где | Имя | Значение |
| --- | --- | --- |
| **Variables** | `CLOUDRU_REGISTRY` | `toniess.cr.cloud.ru` |
| **Secrets** | `CLOUDRU_KEY_ID` | Key ID реестра |
| **Secrets** | `CLOUDRU_KEY_SECRET` | Key Secret реестра |

Реестр общий на аккаунт, splitly соседствует в нём с образами других проектов.

Адрес реестра лежит в переменных, а не в секретах, намеренно: GitHub маскирует
секреты во всём выводе, и в логах вместо тега образа было бы `***`.

Если образ не собрался, отчёты тестов прикладываются к запуску артефактом
`test-results`.

### Почему crane, а не docker push

С реестром в workflow работает только [crane](https://github.com/google/go-containerregistry/tree/main/cmd/crane),
buildx лишь собирает образ в архив. Docker и buildx получают токен реестра
POST-запросом к `id.cloud.ru`, и с раннеров GitHub тот через раз отвечает
`502 Bad Gateway`: отправка падала или зависала на десятки минут без единой
строки в логе. crane получает токен GET-запросом, и этой проблемы у него нет.

### Очистка реестра

После отправки в репозитории `splitly` остаются два образа: только что
собранный и тот, что до этого был `latest`, — на случай отката. Остальные
удаляются по дайджесту вместе со всеми своими тегами. Сбой очистки выкладку
не валит.

Место освобождается не сразу: слои общие между образами, и реестр проверяет,
не используется ли образ работающим контейнером.

## Обновление

Запушить в `main`. После успешной сборки создать в Container Apps новую ревизию
с тегом по хешу коммита, а не `latest`: так видно, какая версия работает,
и есть куда откатиться.

Создание ревизии пока вручную — автоматизировать его можно через API Cloud.ru,
но это отдельная задача.

## Что осталось незакрытым

**Нет ограничения частоты на `/api/v1/auth/login`.** BCrypt с cost 12 стоит
около четверти секунды процессора на попытку — десяток параллельных запросов
кладёт сервис, взлома не требуется. На платформе с автомасштабированием это
обернётся ещё и счётом за ресурсы.

**Swagger UI публичен** на `/swagger-ui.html`. Для демонстрации удобно,
для настоящего прода — лишняя подробность о внутреннем устройстве.
